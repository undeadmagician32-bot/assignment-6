## ① 무엇으로 붙였나
- **직접 구현 + 라이브러리 조합**입니다. 가입·로그인·세션·소유자 검사 흐름은 직접 짰고(`lib/app.js`), 비밀번호를 되돌릴 수 없게 만드는 부분만 **bcryptjs 3.0.3**(널리 쓰이는 bcrypt 의 순수 JS 구현)에 맡겼습니다.
- 사람 알아보는 방법: **서버 세션**. 로그인하면 무작위 32바이트 값을 `pds_session` 쿠키(HttpOnly·SameSite=Lax·Secure)로 주고, 서버 DB(`sessions` 표)에는 그 값의 **SHA-256 해시**만 저장합니다. 만료는 발급 후 **7일**(`expires_at`).
- 그 밖에 쓴 것: `pg 8.23.1`(Postgres 연결), 배포 DB 는 Supabase 의 PostgreSQL. 로컬 개발·테스트용으로 PGlite 0.5.8(개발 전용).
- 비밀번호를 직접 다룬 부분: 해시 계산·비교는 bcryptjs 가 하고, 우리 코드는 길이 검사(10자 이상, 72바이트 이하)와 저장·조회만 합니다. 해시 알고리즘 자체를 직접 만들지는 않았습니다.

## ② 왜 그걸 골랐나
- **함께 검토하고 고르지 않은 방법**
  1. *Supabase Auth(인증 서비스)*: DB 를 이미 Supabase 에 두었지만, 자료 소유자 검사를 어차피 우리 서버 코드가 해야 하고, 이번 과제의 핵심이 "어디를 어떻게 고쳤는지 설명하기"라서 흐름이 보이지 않는 서비스에 맡기면 설명할 내용이 줄어 고르지 않았습니다.
  2. *JWT(Auth.js 등) 토큰 방식*: 서버가 상태를 안 가져 편하지만, 로그아웃·비밀번호 변경 때 이미 발급한 토큰을 즉시 끊기 어렵습니다(과제 기준 C114). 서버 세션은 행 하나를 지우면 바로 끊겨서 골랐습니다.
  3. *argon2*: 더 새로운 방식이지만 네이티브 모듈이라 Vercel 서버리스에서 빌드 문제가 생길 수 있어 순수 JS 인 bcryptjs 를 골랐습니다.
- **bcrypt 를 고른 이유(C102)**: 계정마다 다른 salt 를 해시 문자열에 알아서 붙여 주고(같은 비밀번호도 저장값이 달라짐), 일부러 느리게 계산해 대입 공격 비용을 올리며(cost 12), 오랫동안 검증된 방식이라서입니다.
- **서버 세션을 고른 이유**: 로그아웃·비밀번호 변경·만료를 서버가 직접 통제하고, 쿠키에는 서명용 비밀키가 필요 없어(값 자체가 무작위) 비밀키가 새어 나갈 곳이 없습니다.
- **직접 구현한 이유**: 소유자 검사처럼 "어느 줄에서 막는지"를 보여야 하는 부분이 이 과제의 평가 대상이라서입니다.

## ③ 어디를 어떻게 고쳤나
`db.js`(표), `lib/app.js`(인증·검사), `public/app.js`(화면). 줄 번호는 이 제출 시점 기준입니다.

| 흐름 | 소스에서 지나는 곳 |
|---|---|
| **가입** | 화면 `showAuth()`(`public/app.js`) → `POST /api/auth/register` (`lib/app.js:275`) → `validEmail`/`validPassword` 로 검사 → `bcrypt.hash(pw, 12)` → `users` 에 `INSERT … ON CONFLICT (email) DO NOTHING`(같은 이메일 두 번 불가, 이메일은 소문자로 통일) → `startSession()`(`lib/app.js:246`) 이 세션 발급 → `Set-Cookie` |
| **로그인** | `POST /api/auth/login` (`:289`) → 이메일로 사용자 조회 → 없어도 **더미 해시와 비교**해 시간 차이를 없애고 → 틀리면 항상 같은 문구 `이메일 또는 비밀번호가 올바르지 않습니다`(401) → 맞으면 `startSession()` |
| **로그아웃** | `POST /api/auth/logout` (`:301`) → 쿠키 값의 SHA-256 으로 `sessions` 행을 **DELETE**(서버에서 끊음) → 쿠키 삭제 |
| **자료 조회** | 모든 `/api/*`(공개 4개 제외)는 `handleApi()` 에서 먼저 `userFromRequest()`(`:254`: 쿠키 해시가 `sessions` 에 있고 `expires_at` 이 안 지났는지)로 사용자를 알아내고, 없으면 **401**(`:689`). 그다음 모든 조회·수정에 **주인 조건**이 붙습니다: 목록은 `todoWhere()`(`:53`, 첫 조건이 `plan_id IN (SELECT id FROM plans WHERE user_id = ?)`), 한 건은 `getTodo()`(`:107`)·`getPlan()`(`:124`)·`lockTodo()`(`:421`)에서 `user_id = ?` 가 걸려 있어 남의 것이면 **존재하지 않는 것과 똑같이 404** 를 줍니다. 돌아보기 집계는 `review()`(`:181`)가 같은 `todoWhere()` 를 씁니다. 사용자 ID 는 항상 세션에서 얻고, 주소·헤더·본문에서 온 값은 읽지 않습니다. |

그 밖에 고친 곳
- **6번 자료를 내 계정으로 옮기기**: `plans`·`reflections` 에 `user_id` 열을 더했고(`db.js`), 기존 자료는 주인이 없어 아무에게도 안 보입니다. 환경변수 `LEGACY_OWNER_EMAIL` 로 지정한 이메일이 가입·로그인하면 `claimLegacy()`(`lib/app.js:262`)가 그 자료를 그 계정으로 옮깁니다.
- **CSRF**: 쿠키는 `SameSite=Lax` 이고, 추가로 상태를 바꾸는 요청에 다른 출처의 `Origin` 이 붙어 있으면 403(`lib/app.js:683`).
- **비밀번호 변경**(`/api/account/password`)은 현재 비밀번호를 확인한 뒤 그 계정의 **모든 세션을 지우고** 새 세션 하나를 발급합니다. **계정 삭제**(`DELETE /api/account`)는 비밀번호 확인 후 자료와 계정을 한 트랜잭션으로 지웁니다.
- **내보내기**(`/api/export`)는 본인 자료만, 비밀번호 해시는 제외합니다.

## ④ 안 열리는 것을 확인한 기록
전체 요청·응답 원문은 `docs/evidence-prod.md`(배포 서버)에 있고, 여기에는 핵심만 옮깁니다. 다섯 가지 확인마다 **성공한 요청과 거절된 요청을 나란히** 적었습니다(A·B 는 확인용 임시 계정, 세션 값 가림).

> 아래 표는 `docs/evidence-prod.md` 를 배포 서버에서 실행한 결과로 채웁니다. (배포 후 실행 전까지는 로컬 실행 결과 `docs/evidence-local.md` 를 참고)

| # | 확인 | 성공한 요청 | 거절된 요청 |
|---|---|---|---|
| ① | 로그인 없이 자료 직접 요청 | `GET /api/todos/{A의 id}` (A 세션) → 200 | 같은 주소, 쿠키 없음 → **401** `{"error":"로그인이 필요합니다"}` (목록·내보내기도 401) |
| ② | 남의 자료 **읽기** (양방향) | A가 자기 할 일 → 200 | A→B 의 할 일 → **404**, B→A → **404** |
| ③ | 남의 자료 **수정** (양방향) | A가 자기 할 일 `PATCH` → 200 | A→B `PATCH` → **404**, B→A → **404**, 남의 계획 `PATCH` → **404** |
| ④ | 남의 자료 **삭제** (양방향) | (자기 것 삭제는 정상) | A→B `DELETE` → **404**, B→A → **404**; 거절 앞뒤 건수 A/B 동일, 내용 그대로 |
| ⑤ | 로그아웃 뒤 같은 값으로 같은 요청 | 로그인 상태 `GET /api/plans` → 200 | 로그아웃 뒤 같은 쿠키 값으로 같은 `GET /api/plans` → **401** |

추가 확인(모두 기록 원문에 있음): 주소(`?user_id=…`)·헤더(`X-User-Id`)·본문(`user_id`)에 남의 계정을 적어 보내도 내 자료만 돌아오고 본문의 값은 무시됨 / 목록 응답 5종에 남의 자료 없음 / 비밀번호 변경 뒤 이전 세션 401 / 다른 출처 `Origin` 403 / 같은 이메일 재가입 409 / 비밀번호 틀림과 아이디 없음의 문구 동일 / 로컬 DB 에서 같은 비밀번호로 만든 두 계정의 저장값이 서로 다름(bcrypt `$2b$12$…`).

- **거절 코드**: 남의 자료는 **404**(존재를 감춤)이고 로그인 없음은 401 입니다.
- **거절을 만드는 소스 위치**: `lib/app.js` 의 `userFromRequest`(`:254`)·401 판정(`:689`), 주인 조건 `todoWhere`(`:53`)·`getTodo`(`:107`)·`getPlan`(`:124`)·`lockTodo`(`:421`). 주인 확인은 저장 전에 일어나며(`PATCH /api/todos/:id` 가 `getTodo()` 를 먼저 호출) 거절된 요청은 아무것도 바꾸지 않습니다.
- **세션 값**: 쿠키 값은 URL 에 실리지 않고(HttpOnly 쿠키), 서버는 해시만 저장합니다. 응답·로그에서는 가렸습니다.
- **자동 테스트**: `npm test` 64개 통과(소유자·세션·만료·비밀번호 변경·5일 규칙 포함).
- **비밀키**: 세션 값이 무작위라 서명용 비밀키가 없습니다. 점검 결과(작업 트리·모든 Git 기록·`public/` 에서 연결 문자열·토큰·비밀키 형태 검색) 일치 0건. 환경변수는 `DATABASE_URL`(Vercel 에만 저장)과 `LEGACY_OWNER_EMAIL` 뿐입니다.

## ⑥ 아직 못 막은 것
1. **무차별 대입(비밀번호 추측)**: 로그인 시도 횟수 제한이 없습니다. bcrypt cost 12 가 한 번의 시도를 느리게 만들 뿐, 여러 대에서 계속 시도하면 막지 못합니다. 약한 비밀번호(10자 이상이면 통과)는 결국 맞춰질 수 있습니다.
2. **이메일 확인이 없음 + `LEGACY_OWNER_EMAIL` 선점 위험**: 가입할 때 그 이메일이 본인 것인지 확인하지 않습니다. 따라서 과제 6 자료를 옮겨 받을 이메일로 **남이 먼저 가입하면** 그 자료를 가져갑니다(제가 먼저 가입해서 막았지만 구조적 약점입니다). 또 남의 이메일로 가입해 둘 수도 있습니다.
3. **가입이 누구에게나 열려 있음**: 누구나 계정을 무한히 만들어 DB 를 채울 수 있고(스팸), 가입 시 "이미 가입된 이메일입니다"로 **가입 여부를 알아낼 수 있습니다**(로그인 쪽 문구는 같게 맞췄지만 가입 쪽은 아님).
4. **비밀번호 재설정·2단계 인증이 없음**: 비밀번호를 잊으면 복구 수단이 없고, 비밀번호 하나가 뚫리면 계정 전체가 뚫립니다.
5. **DB 연결 인증서를 검증하지 않음**: Supabase 연결에 `ssl: { rejectUnauthorized: false }` 를 썼습니다(서버리스에서 연결을 쉽게 하려고). 암호화는 되지만 상대가 진짜 Supabase 인지 확인하지 못해 중간자 공격에 취약할 수 있습니다.
6. **소유자 검사가 앱 코드에만 있음**: DB 의 행 단위 보안(RLS)을 쓰지 않았습니다. 앞으로 새 조회를 추가하면서 `user_id` 조건을 빠뜨리면 남의 자료가 보일 수 있고, DB 에 직접 접근하는 사람은 모든 자료를 봅니다.
7. **세션 보호가 단순함**: 세션은 IP·기기에 묶여 있지 않아 쿠키를 훔치면 7일간 그대로 쓸 수 있고, 로그인 기록·이상 로그인 알림이 없습니다. CSRF 는 SameSite·Origin 검사에만 기대고 별도 토큰은 없습니다.
8. **로그 기록 없음**: 누가 언제 로그인에 실패했는지 남기지 않아 공격이 있어도 알 수 없습니다.

## ⑦ 5일 기록과 계획 규칙 변경
기능은 구현했고(`/api/experiment*`, 화면 "5일 기록" 탭), **실제 5일 기록은 사용하면서 쌓는 중**입니다. 아래 칸은 5일이 끝난 뒤 채웁니다.

- **고정한 것(1일차에 서버가 한 번만 저장, 이후 수정 불가)**: 질문 한 문장(본인 입력), 지표 = **하루 계획 시간과 실제 시간의 차이**, 단위 = **분**, 계산 규칙 = *실제 − 계획*.
- **계산 규칙(서버에 저장·화면에 표시)**: 빠진 날은 0으로 치지 않고 평균에서 제외 / 같은 날짜에 다시 저장하면 마지막 값으로 교체(날짜는 서버가 서울 기준으로 정함) / 차이 절댓값 240분 초과는 "튀는 값"으로 표시하되 제외하지 않음 / 평균은 소수 첫째 자리에서 반올림(.5 는 0에서 먼 쪽) / 주 시작은 월요일.
- **순서 강제(서버)**: 질문 고정 → 1·2일차 기록 → 계획 규칙 **한 번** 변경(2일차 기록이 정확히 있을 때만 가능, 변경 시각·이유·1·2일차 기록 ID 저장) → 3일차부터 기록(규칙 변경 없이는 3일차 저장 거절) → 최대 5일.
- 5일 결과(날짜별 값, 규칙 변경 기록, 전후 비교, 손으로 더한 값과의 대조): **(5일 뒤 작성)**

1. **어디로 가나요**: 결과물 주소를 새 시크릿 창에서 엽니다. 첫 화면이 로그인 화면입니다(계정 없이 여기까지 열림).
2. **세 단계 안에 무엇을 하나요**: ① 가입 탭에서 아무 이메일과 10자 이상 비밀번호로 가입 → ② 계획·할 일을 하나 만들고 로그아웃 → ③ 같은 주소 `/api/plans` 를 로그인 없이 열어 봅니다.
3. **무엇이 보이면 통과인가요**: ③에서 자료 대신 `{"error":"로그인이 필요합니다"}`(401)가 보이고, 다시 로그인하면 내 자료만 보입니다. 다른 계정에서는 내 자료가 목록에 없고 id 를 직접 불러도 404 입니다.
4. **안 될 때는 무엇이 보이나요**: 화면에 붉은 글씨(예: "이메일 또는 비밀번호가 올바르지 않습니다", "이미 가입된 이메일입니다")가 뜨고, 서버 문제면 "서버 오류가 났습니다"가 뜹니다. 서버 상태는 `/api/health` 로 확인합니다.
